Task Tracer Design

A gem5 SimObject that watches a restored Linux guest from outside: every context switch, fork, exec, exit and OpenCode tool call, stamped in ticks and committed instructions, without changing a single simulated statistic and without recapturing any checkpoint. This page explains how it works and how we know it is right.

The problem

The agentic checkpoints are OpenCode coding agents replayed model-free inside an Ubuntu arm64 guest: 27 SWE-bench-Multilingual tasks, 132 checkpoints, one vCPU, kernel 6.8.12 with KASLR and KPTI. We expected their cost to sit in short, fragmented tool calls and frequent context switches. To compare the core's behaviour around those events against steady state, a run has to say:

  • which guest task is on the CPU, and every switch, fork, exec, exit and rename, with names;
  • every tool call (name, input, start and end);
  • each stamped with the simulated tick and a global committed-instruction count that joins with gem5's stats.

Two constraints rule out most designs: the measurement must not change, and the 132 checkpoints cannot be recaptured.

Why not gem5's own tools

Every option was checked against the source on this branch. The guest runs with KASLR and the checkpoints carry an empty kernel symbol table on purpose, which breaks everything that names kernel code by link address.

Hooks

The tracer places a gem5 PC event on the first instruction of a few guest kernel functions. A PC event fires when that instruction is about to commit: O3 services it in commit, so it never fires on a wrong path, and the function's arguments are in x0..x2. PC events belong to the System and follow the thread across m5.switchCpus, so tracing is continuous from the atomic core to O3 and back.

__arm64_sys_execve(at)user filename and argv from pt_regsremembered for the exec
perf_event_comm(task, exec)the new name, the exec flagexec or rename
do_exit(code)exit codeexit
vfs_write, vfs_readfile path from the dentry chain, bufferwrite, read

At start-up the tracer walks init_task.tasks and each thread ring and writes a snapshot of every task alive at the restore. Choices that were found the hard way:

  • Execs come from perf_event_comm. In this kernel begin_new_exec contains an inlined copy of __set_task_comm, so the out-of-line symbol only sees prctl renames; the first runs showed processes forking as python3 and exiting as docker with no exec. With no aarch64 disassembler on the host, the callers' bl targets were decoded from the ELF bytes. Pending execs are keyed by task_struct address, since a non-leader thread that execs takes its leader's pid.
  • Tool calls come from SQLite, not the event log. OpenCode's JSON event stream only marks a call's end. Its session database writes the 4 KiB page holding a tool part's row at each state change, so recording OpenCode's writes gives pending, running and completed at exact instruction counts.
  • current is SP_EL0, which arm64 Linux uses to hold it at EL1.

Reading guest memory without disturbing the simulation

The first version read guest memory through gem5's TranslatingPortProxy. An O3 pair, the same 1M + 5M window with and without the tracer, showed IPC moving from 0.635 to 0.649 and 5,377 stats lines changing. The cause: ArmISA::MMU::getTE does its first TLB lookup as a timing access even for a functional translation, so a "read-only" access updates TLB replacement state and statistics, and can fill the L1 TLB from the L2. Fixing the MMU would have changed every syscall-emulation result on the fork.

So the tracer walks the guest's own stage-1 page tables in software (EL1&0, 4 KiB granule, TTBR0/1_EL1 by VA bit 63, start level from TCR_EL1.T0SZ/T1SZ) and reads descriptors and data through System::physProxy. Permissions are not checked, so user buffers are readable from kernel-side hooks. Kernel addresses always translate through swapper_pg_dir, because a restore that lands at EL0 has TTBR1_EL1 pointing at KPTI's trampoline table, where the kernel is not mapped. A failed read is recorded as null and never stops the simulation. After the change the pair is byte-identical.

Finding the kernel: KASLR slide and struct offsets

The slide is derived from the restored state, following RPoint's landing.py:

  1. TTBR1_EL1 holds the physical address of swapper_pg_dir (at EL1) or tramp_pg_dir (at EL0 with KPTI).
  2. Both sit at fixed offsets in the contiguous kernel image, so each candidate gives an image base.
  3. The candidate whose init_task.comm reads swapper/0 is right.
  4. slide = pa_text + kimage_voffset − link(_text); hook addresses are vmlinux symbols plus the slide.

This works on all 27 local checkpoints, including the five whose provenance has no landing label. If an expected slide is given and differs, the run stops.

Struct offsets come from gdb evaluating &((struct T *)0)->field on the vmlinux, which follows anonymous unions. The kernel was built with reduced debug info: task_struct, file, dentry, qstr and pt_regs have layouts, while mm_struct, linux_binprm, path and the cgroup structs do not. That is why exec paths come from the syscall's arguments, why there are no cgroup names, and why two layouts are assumed (struct path with its dentry at +8, list_head.next at 0, both unchanged since 2.6). A missing field is fatal, because a guessed offset would produce plausible garbage.

Instruction counts

Every event carries insts, gem5's total committed instructions over all CPUs since the restore. It keeps counting across core switches and stats resets, and stats blocks record the same count, so events and blocks join exactly. Each event also carries uinsts, the user-mode (EL0) part, from a counter added to BaseCPU and incremented in the simple, O3, Minor and KVM CPUs.

A bug found while validating it. The first uinsts was incremented next to gem5's numUserInsts stat. But O3's instruction total leaves out NOPs and instruction prefetches while that stat counts them, so pure user slices showed −1% to −3% kernel work. The O3 increment moved to CPU::instDone. Afterwards a long rg slice's kernel share matched gem5's own stats, 54.1% against 54.2%.

The switch event also carries the instructions and ticks from __schedule's entry to __switch_to: the scheduler's direct cost, excluding the system call or interrupt that led to it.

What it has shown so far

Provisional. These come from a few windows and one sweep per configuration; they are working hypotheses in the project wiki and may change with new runs.
  • About a fifth of agentic instructions are the benchmark's own polling. The model-free replay driver runs docker inspect every 50 ms of guest time while it waits, each a fresh Go process of about 40M instructions sharing the vCPU with the agent. The tracer made it visible; analyses now report shares with and without it.
  • The scheduler is cheap; what surrounds a switch is not. The scheduler path takes a median of ~1,800 instructions and ~1,700 cycles. Blocks containing a switch run at IPC 0.60 against 1.00, with three times the kernel share, and the same scheduler code takes 4,705 cycles instead of 1,650 during a tool's process churn: cold state, not scheduling.
  • The cost depends on who runs. Pipe hand-offs between two small processes raise IPC; short-lived shells, forks and execs cut it by a third to a half.
  • A tool call is mostly harness work. A 45-line file read takes about 170M instructions from running to completed, most of it OpenCode persisting state and its JavaScript runtime; a two-command bash call took 1.02G instructions, of which the tool processes ran about 70M.
  • The tools fence is inactive in the replay guests: no cgroup.procs writes, and fenced tools share OpenCode's cgroup set.

Limits

  • One kernel's internals: gdb-derived offsets, a 4 KiB-only stage-1 walk, hooks chosen around 6.8.12's inlining. A new kernel means rerunning kernel_layout.py and rechecking the hooks.
  • One vCPU, so switch counts are higher than on a multi-core machine.
  • The user/kernel split is per time slice, in instructions; cycles per mode would need a hook on exception entry and return.
  • No cgroup or container names, and no command lines for processes that predate the checkpoint (recording mm->arg_start..arg_end in the snapshot would fix this).
  • The task on the CPU at the restore is named only when it first switches out.
  • Reads have no data and only cover read and pread; paths stop at mount points.

Extending it

  1. Find the function in the vmlinux (nm <vmlinux> | grep <name>) and check it is not inlined at the call sites you need.
  2. Add a handler void myHook(ThreadContext *tc) to LinuxTaskTracer, register it in startup() with add("symbol", &LinuxTaskTracer::myHook), read arguments from int_reg::X0.., and write with begin("name"), writeTask(...), end().
  3. New struct fields go into OFFSETS in kernel_layout.py and as a Param.Unsigned of the same name in ArmLinuxTaskTracer.py.
  4. Read guest memory only through readVirt, readU64 and readString, never a TranslatingPortProxy, then rerun the no-perturbation check.

Another kernel needs only its own vmlinux, since the slide and offsets are derived from it. The process labels hold for any Linux guest; only the tool-call parsing is specific to OpenCode, and --task-trace-process points the read and write hooks at another process.
