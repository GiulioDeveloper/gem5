Long Runs Guide

How to simulate billions of instructions of an agentic task in detail, keep every committed instruction and every stats block in under a gigabyte, and turn the result into per-process numbers you can compare across core configurations.

What a long run is

A sweep window simulates 400 million instructions of a checkpoint in detail. That is a fraction of a second of the guest: one tool call, or part of an agent's think step. A long run simulates billions (15G in our first study), which covers whole agent rounds, several tool calls and the tests they launch. That lets you split the run by process and ask how the agent harness behaves against the tools it calls.

The problem is volume. Left alone, gem5 would write about 20 GB of statistics text and, for the instruction trace, around 225 GB of gzipped Exec trace per run. The tools below keep a whole run under 1 GB, check themselves at every step, and read the compact files directly, so you never expand them.

1 · LAUNCH

pc-trace.sh

Detailed run with the task tracer, the PC trace and stats blocks.

2 · COMPACT

automatic

Exec trace reduced live; stats turned into a table at the end.

3 · CUT

split_stall.sh

Moves a guest hang at the end of the run aside.

4 · CHECK

check_pc_slices.sh

Traces and stats agree, slice by slice.

5–8 · ANALYSE

compare_runs.sh

Per run, across configurations, per process, code footprint.

Before you start

  • Python 3.14 or newer for the readers of the compressed files (they use the built-in compression.zstd). The launcher picks the interpreter from PY=.
  • The zstd command-line tool, for the stall split and the slice check.
  • A built build/ARM/gem5.opt and the checkpoints in /home/snapshots/gem5-ckpts (or CKPTS=).
  • A possible hang. Plan for the run to stop doing useful work partway through (step 3). Until that is understood, watch run.log: an IPC near 0.008 that never recovers means the guest has hung, and you can stop the run.
  • Time and memory. About 30 hours per 15G instructions, and up to ~9 GB of memory per run by the end. Six runs at once used ~51 GB.
  • Run every command from the repository root. Put launch scripts and outputs under runs/, which git ignores.

1 · Launch

OUTDIR=runs/my-study/baseline O3="1 20000000 15000000000" \
    run_scripts/tasktrace/pc-trace.sh rubocop-13560 0 \
    --stats-interval-insts 200000

O3= gives the three phases: settle on the atomic core (1 instruction), warm the caches (20M), then the detailed region (15G). The task name is the checkpoint name without agentic-; the 0 is ignored when O3 is set. Everything after it goes to the gem5 config script, so configuration flags go there too, for example --cache-scale 4 or --infinite-btb --infinite-tlb.

--stats-interval-insts 200000 dumps gem5's statistics every 200K instructions. Each of these stats blocks lines up exactly with the task trace, which is what lets you attribute misses to processes later. 200K is fine-grained enough to see the cost of a context switch; larger blocks blur it.

Several configurations at once: start each run with setsid nohup … & and wait a minute or two between starts, so the restores do not all claim memory at the same moment. runs/rubocop-15G/launch.sh is a working example that launches six.

What to expect

measured on six 15G rubocop runs
speed124–176K instructions per second; ~22K/s while the guest is hung
wall time30–33 h without a hang, 40 h or more with one
memory~3 GB at the start, ~8.6 GB at the end (the guest touches more memory as it goes)
progressrun.log prints the committed instruction count and IPC every 10 kHz of simulated time

Stopping a run early

Send SIGTERM to the gem5 process, not to the launcher script. gem5 exits, and the launcher then finishes the PC trace and converts the statistics as it would at a normal end. Two of our six runs were stopped this way after 42 hours, and both ended with complete, checked files.

2 · Compaction (automatic)

You do not run anything for this step. It is worth knowing what happens, because the files you get are not the ones gem5 normally writes.

Statistics
stats.txt · 20–22 GB
stats.tsv.zst · 0.25–0.28 GB
Instruction trace
gzipped Exec trace · ~225 GB (never written)
pc_trace.zst · 0.37–0.54 GB

The statistics table: stats.tsv.zst

gem5 writes every stat name again in every block, which is most of the 20 GB. At the end of the run the launcher calls stats_table.py, which writes the names once as a header and then one row of numbers per block, compressed with zstd. Before deleting stats.txt it reads both files back and compares every value; the run log then says checked. All six 15G runs converted 80–83× smaller. Every analysis script reads either form, so you rarely notice the difference. Set KEEP_STATS=1 to keep the text file too.

The PC trace: pc_trace.zst

gem5's Exec trace prints a long line for every instruction. Instead, gem5 writes it into a named pipe, and pc_trace.py reads it as it comes and keeps one short line per committed instruction: the address only when the program jumped (otherwise it is the previous address plus 4), and the instruction's name. Every time the guest switches tasks, it inserts a marker naming the task that runs next. The result is about 0.035 bytes per instruction, and it rebuilds the exact sequence of committed addresses. You can read it in Python with pc_trace.read_pc_trace(path).

3 · Cut off a guest hang

Long runs can hang, and we do not fully understand why yet. Four of our six 15G rubocop runs stopped doing useful work at the same moment, about 4.6 simulated seconds after the restore; the two fastest configurations finished first. From then on the guest runs one kernel thread in a spin and never switches tasks, and gem5 slows to ~22K instructions per second. Our working hypothesis is that the kernel's first reseed of its random number generator asks the firmware for random bits and the call lands in a stub that loops forever. That comes from one checkpoint's trace and is not confirmed: which checkpoints hang, when, and how to prevent it are open questions for a future investigation. Cutting the hang off, below, is a workaround that lets you analyse the useful part of a run, not a fix.

Before analysing a run, move the hung part out of the way:

analysis_scripts/tasktrace/split_stall.sh runs/my-study/baseline

Because the cause is not settled, the script does not look for any particular cause. It finds the hang from the data: the run kept going for more than 0.1 simulated seconds after the task trace's last event (STALL_MIN= changes the threshold). The stats blocks before it stay where they are; the rest move to <run>/stall/, and the PC trace is cut at its last task marker. It deletes the original files only when the blocks, stats rows and PC-trace instructions of both parts add up exactly, and records the split in stall/SPLIT.txt. A run that did not hang is left untouched, so it is safe to run on every run.

It needs the statistics as a table and refuses to run while a stats.txt is still present, since the readers would pick the text file and ignore the split.

4 · Check the data

Three independent records describe the same run: the task trace (who ran, with instruction counts), the PC trace (every instruction) and the stats blocks. These checks confirm that they agree.

analysis_scripts/tasktrace/check_pc_slices.sh runs/my-study/baseline

This counts the instructions between every two task markers of the PC trace and compares them with the task trace's count between the same two context switches. Every slice should match; the output reads like slices equal without NOPs 22631, equal with NOPs 0, different 0. (On the detailed O3 core, the tracer's count leaves out NOP instructions, so the matches appear under "without NOPs".) It exits with an error if any slice differs, and takes about 10 minutes per 15G instructions.

Two more checks run on their own: trace_analysis.py prints how far gem5's user-mode share per block is from the trace's (around 0.05 is normal), and pc_footprint.py checks the instruction count at every task marker as it goes.

5 · Analyse one run

python3 analysis_scripts/tasktrace/trace_analysis.py runs/my-study/baseline
python3 analysis_scripts/tasktrace/window_view.py runs/my-study/baseline

Both write to <run>/analysis/. trace_analysis.py works out who ran when, the tool calls, and a table of the stats blocks (blocks.csv: IPC, user-mode share and miss rates per block, and which process filled it). window_view.py builds window.html, an interactive page with the per-block metrics and the trace's events on the same axis. Both stream the statistics, so a 75,000-block run needs little memory.

6 · Compare configurations

For one checkpoint run under several configurations (a limit study, a cache sweep), one script does steps 5 and 7 for every run and compares them:

analysis_scripts/tasktrace/compare_runs.sh runs/my-study/compare \
    runs/my-study/baseline runs/my-study/cache4x runs/my-study/cache8x
  • The run directory names become the labels, and the first run is the baseline.
  • Each run gets its own analysis (step 5).
  • A common region, the first N blocks of every run (N = the shortest run), goes through the sweep tools: OUT/compare/ has every metric per configuration and its change against the baseline, as a CSV and an HTML page.
  • The per-process views (step 7) go to OUT/process_views.csv, with an IPC summary in OUT/process_views.txt.
Same instructions, different work. The guest's agent session runs on wall-clock time: timeouts, polling, waiting for Docker. A faster core gets further into the session in the same number of instructions, so the common region of a fast configuration contains more tool work and less waiting. On rubocop the tools' share of instructions grew from 3.6% in the baseline to 19.5% in the fastest configuration. Whole-region numbers therefore mix the effect of the hardware with a change of workload. Compare per process (next step) instead.

7 · Per-process views

python3 analysis_scripts/tasktrace/process_views.py \
    runs/my-study/baseline runs/my-study/cache8x -o views.csv

The run is cut at every context switch, and each slice goes to the task that ran in it. Tasks are grouped by who launched them:

groupwhat is in it
harnessOpenCode, all its threads, and what it launches itself outside a tool call (its git snapshots)
toolseverything started by a tool call: processes under bash.fence-real or rg.fence-real, the wrappers of OpenCode's shell and search tools (for rubocop: bundle, ruby, gem, …)
driverthe replay driver (run.sh and its children) and the Docker daemons. This is our replay machinery, not part of the agent, so it is kept apart.
otherevery other user process
kernelkernel threads and the idle task

For each group and each process you get: the share of time and of instructions, the split between user and kernel mode, IPC, and misses per 1,000 instructions (L1I, L1D, L2, branch, BTB, iTLB, dTLB). Each comes in four views that answer "how much of this is the cost of being switched in and out?":

  • all: every slice, whole. IPC and the user/kernel split are exact, from the trace's own cycle and instruction counts; misses are shared out from the stats blocks by instruction overlap.
  • skip1: drops the block holding the switch in and the one holding the switch out.
  • skip3, skip6: drop 3 or 6 blocks at each end, so the first 0.6M or 1.2M instructions after the process is switched in and the same before it is switched out.

The gap between all and the trimmed views is the cost of running next to a switch: cold caches, branch predictors and TLBs after another process has used them. A group's numbers are the sum of its processes, so the harness is also trimmed where OpenCode hands over to its own git snapshots.

8 · Code footprint

python3 analysis_scripts/tasktrace/pc_footprint.py runs/my-study/cache8x

From the PC trace alone, independent of the simulated caches: how much code each process, PID and thread runs (distinct instructions, cache lines and pages), how that compares with the L1I and L2 sizes, the hit rate a fully associative LRU cache of each size would get, how soon each instruction repeats, and how many distinct branches there are by type. Output in <run>/footprint/, including report.html, a per-thread page. Since the code a run executes barely depends on the core configuration, one run per checkpoint is enough. It takes 15–45 minutes and up to 8 GB of memory per 15G instructions.

Reading the numbers

  • Sum, then divide. Window IPC is total instructions over total cycles. The average of per-block IPCs is higher (1.147 against 0.921 for the rubocop baseline), because fast blocks and slow blocks have the same number of instructions.
  • Compare per process, not per window, for the work-mix reason above.
  • Trimmed views of small groups are noisy. Tools and kernel threads run in short bursts; skip6 may keep only a handful of blocks, or none. The CSV gives the number of kept blocks.
  • The PC trace reducer warns about "switch ticks before their Exec tick" (46–68 per 15G run). On the O3 core that is expected and does not affect the result.
  • The PC trace has committed instructions only: no wrong-path fetches.

Worked example: rubocop, 15G instructions, six configurations

The first study with these tools ran rubocop-13560 under six configurations: the baseline, an infinite BTB with an infinite L2 TLB, and both of those with caches ×4 and ×8 larger. Group IPC per slice, before the hang, and its change against the baseline:

grouptimebaselineinf. BTB+TLBcaches ×8both, ×8
whole task100%0.909+9.8%+27.2%+32.5%
harness73.9%0.923+7.9%+21.4%+27.3%
tools2.8%1.147+10.7%+34.3%+38.4%
driver and Docker20.7%0.891+7.3%+19.5%+23.5%

The tools run about a quarter faster than the harness and gain more from every configuration. Trimming 3 blocks at each switch raises the baseline IPC by 11% and lowers the gains (the infinite BTB+TLB from +9.8% to +6.5% over the whole task), so a good part of what these structures buy is faster recovery after a switch. These are results from one task and should be read as such. Details are on the experiment's wiki page, docs/wiki/experiments/2026-10-23-rubocop-15g-cache-btb-tlb.md.

All commands

For a study with a baseline and two configurations, from the repository root:

# 1. launch (one per configuration; ~30 h each for 15G)
mkdir -p runs/my-study
for c in baseline:"" cache4x:"--cache-scale 4" cache8x:"--cache-scale 8"; do
    name=${c%%:*} flags=${c#*:}
    OUTDIR=runs/my-study/$name O3="1 20000000 15000000000" setsid nohup \
        run_scripts/tasktrace/pc-trace.sh rubocop-13560 0 \
        --stats-interval-insts 200000 $flags > runs/my-study/$name.log 2>&1 < /dev/null &
    sleep 90
done

# 2. compaction happens at the end of each run; look for "checked"
grep checked runs/my-study/*.log

# 3. cut off the guest hang (no-op on runs that did not hang)
for r in runs/my-study/{baseline,cache4x,cache8x}; do
    analysis_scripts/tasktrace/split_stall.sh $r
done

# 4. check the PC trace against the task trace
for r in runs/my-study/{baseline,cache4x,cache8x}; do
    analysis_scripts/tasktrace/check_pc_slices.sh $r
done

# 5-7. per-run analysis, comparison, per-process views
analysis_scripts/tasktrace/compare_runs.sh runs/my-study/compare \
    runs/my-study/baseline runs/my-study/cache4x runs/my-study/cache8x

# 8. code footprint, on one run
python3 analysis_scripts/tasktrace/pc_footprint.py runs/my-study/baseline
