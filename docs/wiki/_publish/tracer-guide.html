Task Tracer Guide

How to see, inside a gem5 restore of an agentic or SPEC checkpoint, which guest process or thread is running, when it switches, forks, execs and exits, and when each OpenCode tool call starts and ends. Every event is stamped in simulated ticks and committed instructions, so it lines up with gem5's statistics.

What you get

For one restored checkpoint, a traced run produces:

outputwhat it is
tasktrace.jsonlA snapshot of every guest task at the restore, then one JSON line per event: context switch, fork, exec (with path and argv), rename, exit, OpenCode's write() (with payload) and read() calls, and writes to any cgroup.procs.
intervals.csv + stats.txtOptional: gem5 stats dumped every N instructions of the detailed region, each block with its tick and instruction range.
analysis/*.csv, summary.mdPer process, per place, per tool call, per switch cause, per stats block, and event-aligned tables.
analysis/schedule.htmlAn interactive timeline of who ran when.
analysis/window.htmlPer-block microarchitecture metrics as bar charts, on the same axis as the schedule.
IN GEM5

Tracer

--task-trace on virt_run.py or fs_run.py attaches LinuxTaskTracer, which writes the trace while the guest runs.

IN GEM5

Stats blocks

--stats-interval-insts N dumps and resets stats every N committed instructions and writes intervals.csv.

ON THE HOST

Analysis

trace_analysis.py, trace_view.py, window_view.py read the finished run. Python stdlib only.

Setup

  • A gem5 build with the tracer: scons build/ARM/gem5.opt -j$(nproc) from the repository root.
  • gdb on the host. It reads struct offsets from the guest's vmlinux; an x86 gdb reads the aarch64 file fine.
  • The checkpoints live outside the repository in /home/snapshots/gem5-ckpts. Every script takes that root from CKPTS, so CKPTS=/other/copy points them elsewhere.
  • Python 3 for the analysis. matplotlib is needed only for the optional PDF figures; on hosts without it, make a venv with python3 -m venv --without-pip runs/venv && pip --python runs/venv/bin/python install matplotlib.

Run everything from the repository root. Runs write into runs/, which git ignores.

Running a traced restore

Set the common agentic arguments once. TASK is a checkpoint name without the agentic- prefix, such as gin-2121.

AGENTIC=${CKPTS:-/home/snapshots/gem5-ckpts}/rpoint_ckpts/agentic
TASK=gin-2121
CPT=$AGENTIC/checkpoints/agentic-$TASK/cpt.0
COMMON="--disk-img $AGENTIC/images/rpoint-ubuntu-24.04-v21.img \
  --kernel $AGENTIC/kernel/arm64-linux-kernel-6.8.12-1.0.0 \
  --bootloader $AGENTIC/bootloader/boot_v2_qemu_virt.arm64 \
  --release kvm-host --progress-interval 10kHz"

Event trace only, on the atomic core

The quickest way to see what a checkpoint is doing: about 1.7 million instructions per second.

./build/ARM/gem5.opt --outdir=runs/trace-$TASK configs/garfield/arm/virt_run.py \
  --restore-dir $CPT $COMMON \
  --atomic-only --atomic-max-insts 2000000000 \
  --task-trace

Or run_scripts/tasktrace/atomic.sh $TASK 2000000000.

A detailed O3 window in stats blocks

Fast-forward on the atomic core, warm up, then simulate a region on the Neoverse V2 model in fixed-size blocks. O3 runs at roughly 95 to 200 thousand instructions per second.

./build/ARM/gem5.opt --outdir=runs/o3-$TASK "--stats-file=stats.txt?desc=False" \
  configs/garfield/arm/virt_run.py --restore-dir $CPT $COMMON \
  --settle-insts <S> --warmup-insts 20000000 \
  --detailed-insts <N> --stats-interval-insts 200000 \
  --tail-insts 100000000 \
  --task-trace

Or run_scripts/tasktrace/o3-window.sh $TASK <S> 20000000 <N> 200000. ?desc=False drops stat descriptions; a block is then about 320 KB, so plan on 320 KB × N / block size.

A SPEC CPU 2026 checkpoint

run_scripts/tasktrace/spec-window.sh 714.cpython_r 1 20000000 200000000 200000

Restores the benchmark's SimPoint through fs_run.py, 1 atomic instruction, 20M warm-up, 200M measured in 200K blocks. SPEC guests have no OpenCode, so the trace is the schedule only; the benchmark runs alone and is rarely switched out.

Flags

flagmeaning
--task-traceAttach the tracer; writes <outdir>/tasktrace.jsonl. Without it the drivers behave exactly as before.
--task-trace-process NAMEProcess whose writes (with payload) and reads (path, size, offset) are recorded. Default opencode; empty disables both.
--task-trace-slide HEXExpected KASLR slide. Defaults to the checkpoint's provenance.json; the run stops if the derived slide differs.
--stats-interval-insts NDump and reset stats every N committed instructions of the detailed region and write intervals.csv. 0 dumps once.
--tail-insts MAfter the detailed region, switch back to atomic and run M more instructions, still traced, to see events that finish late.
--disable-fdp, --infinite-btb, --infinite-tlbCore configuration switches; any extra argument after a run script's positional ones is passed through.

Placing a window on an event

Detailed simulation is slow, so find the interesting point on the atomic core first.

  1. Run the atomic trace long enough to cover the event.
  2. Run trace_analysis.py and read the event's instruction count from analysis/tools.csv or processes.csv.
  3. Restore with --settle-insts hundreds of millions of instructions before that count, a region long enough for the whole event, and --tail-insts.
  4. Locate the event again in the O3 trace before choosing phase boundaries.
Events move between atomic and O3. The replay driver's polling and the guest's timers follow simulated time, so a different core places events at different instruction counts: by a few million in one window, by about 130 million in another. Never reuse atomic positions as O3 boundaries.

Rounds. The restore starts inside RPOINT_REPLAY_ROUND 1. The guest prints RPOINT_REPLAY_ROUND N on <outdir>/board.terminal; each later round holds one model response and its tool calls, billions of instructions apart. To cover a whole round, run atomic until the next marker appears, then stop with SIGINT: the trace is flushed line by line.

How processes are labelled

Labels are facts the trace supports, never guesses at purpose:

  • kind: user, kernel thread, or idle.
  • place: host, or container <top> (<tgid>), a namespace set named after its first process.
  • launch tree: the topmost ancestor below systemd, such as run.sh (519) or python (1003).
  • lineage: names from that root down, such as run.sh > sudo > make > sh > uv > python3 > docker.

How tool calls are found

OpenCode stores its session in SQLite with a write-ahead log. Each state change of a tool part (pending, running, completed or error) is one write() of the 4 KiB page holding that JSON row, which the tracer records. So every transition has an exact instruction count. read, edit and write run inside OpenCode; bash and ripgrep run as separate processes (bash.fence-real, rg.fence-real). A call's kind is observed from which descendants ran, not inferred from the tool name.

The two viewers

Schedule timeline: schedule.html

A whole-run strip you can brush, a tool-call track, a CPU track, and one lane per process with exec, fork, exit, tool I/O and cgroup marks. Colour by process, launch tree or place; click a legend entry to hide it. Each bar's darker bottom band is its kernel-mode share and its dark end is the scheduler path. Open view.json loads any other run's schedule.view.json, so one page serves every run.

Window metrics: window.html

One bar chart per metric on a shared instruction axis, one bar per stats block, with the schedule underneath. The dashed line is the metric over the whole window, computed from summed stats. Step through events of one kind and cause with the arrow keys, see each metric's mean and quartiles around those events, and add any stat with --metric KEY=STAT[/insts|/cycles].

One known issue. The "BTB misses" row reads btb.misses, which is always 0 with the decoupled front end. Use the BTB-miss mispredicts row instead.

Sweeps and comparisons

A sweep runs one traced window per local checkpoint: every SPEC benchmark (200M instructions) and every agentic task (400M), each after 1 atomic instruction and 20M of warm-up, in 200K-instruction blocks. Each finished run is analysed and marked done; rerunning with the same directory resumes.

nohup run_scripts/tasktrace/smart_sweep.sh > runs/sweep.log 2>&1 &

Use smart_sweep.sh rather than sweep.sh. Runs need 2.5 to 22 GB each (nushell-13831 is the largest), and unguarded parallel sweeps once got the whole terminal killed by the OOM daemon. The smart version starts a run only when there is memory for its measured peak, across all sweeps sharing its lock.

variablemeaning
PARMost runs in parallel per sweep.
EXTRAFlags for every run, such as --infinite-btb. Resuming with different flags is refused.
BASELINEA sweep to compare against when this one finishes.
ONLY, SETTLE, WARM, IVL, SPEC_DET, AGENTIC_DETRestrict checkpoints; window settings.
RESERVE_GB, STAGGER, LOCK, PEAKSMemory gating (defaults 8 GB, 60 s, a per-user lock, runs/sweep/mem_peaks.tsv).

sweep_summary.py <sweep> writes one row per checkpoint and a violin page per suite. --skip-insts 100e6 leaves out each window's first 100M instructions without re-simulating. sweep_compare.py A B [C ...] pairs checkpoints across up to eight sweeps and reports each one's change against the first:

runs/venv/bin/python analysis_scripts/tasktrace/sweep_compare.py \
    runs/sweep/<fdp> runs/sweep/<nofdp> runs/sweep/<infbtb> \
    --labels FDP no-FDP inf-BTB --pdf

Trace format

One JSON object per line, flushed per line. Every line has tick (1 ps), insts, uinsts and event.

eventextra fields
startkaslr_slide
snapshottasks, count: every task alive at the restore
switchprev, next, same_mm, sched_insts, sched_ticks
forkparent, child (same tgid means a new thread)
exec / renametask; path and argv for execs seen after the restore
exittask, code
write / readtask, file, path, count; writes add data, reads add pos

A task is {pid, tgid, ppid, comm, process, kernel_thread, kthread, ns, cg}. ns and cg are kernel pointers used as identities (same value, same container or cgroup set), comparable within one run only. Guest strings are byte strings: recover the bytes with s.encode("latin-1").

{"tick":209306074077,"insts":1756030,"event":"switch","same_mm":true,
 "prev":{"pid":1308,"tgid":1235,"comm":"JITWorker","process":"opencode",...},
 "next":{"pid":1303,"tgid":1235,"comm":"JITWorker","process":"opencode",...}}

Reading the numbers

  • Aggregate raw counts, never ratios. IPC over blocks is total instructions over total cycles. With equal-instruction blocks the window IPC is the harmonic mean of block IPCs: in one window 0.956 against a mean bar of 1.21. trace_analysis.load_blocks() gives the raw counts.
  • Which instruction count. insts is the global committed count since the restore, never reset, the same basis as intervals.csv. uinsts is its user-mode part. gem5's numInsts stats include NOPs and must not be mixed with insts. The progress line counts micro-ops, about 12% more.
  • Thread, process and kernel switches are classified by tgid, not by address space. A change of process through a kernel thread (opencode -> rcu_preempt -> cc1plus) also counts as a process switch, marked via kernel.
  • The replay driver is in the measurement. About a fifth of agentic instructions are the host's docker inspect polling (the run.sh launch tree). Report shares with and without it.
  • A metric shift near an event is not the event's effect until you have checked a control: 714.cpython_r changes phase with no event at all.
  • Pick fine blocks (100 to 200K instructions) to separate a switch from the next task's cold start.

Debugging

  • --debug-flags=TaskTracer, placed before the config script, prints the derived slide, every hook address and every vfs_write.
  • No switch for a while is normal inside compilers, linkers and JIT code: a 4 ms scheduler tick is about 10M instructions.
  • "KASLR slide … disagrees": the checkpoint and its metadata do not belong together, or the vmlinux is not the guest's.
  • "cannot derive the KASLR slide": almost always --kernel is a different kernel from the one the guest booted.
  • kernel_layout.py reports unresolved fields: the vmlinux lacks debug info for that struct. Run it by hand with python3 configs/garfield/arm/kernel_layout.py <vmlinux>.
  • A restore that runs but gives uniform IPC across tasks is a corruption signature. Check --release kvm-host, the disk delta and the ASID fix before trusting it.

Known limits

  • One vCPU: switch counts are higher than on a multi-core machine.
  • The user/kernel split is per time slice, in instructions, not cycles.
  • The scheduler cost covers __schedule to __switch_to only.
  • No cgroup or container names, and no command lines for processes that existed before the checkpoint.
  • The task running at the restore is named only when it is first switched out.
  • Reads are recorded without data, and only through read and pread; paths do not cross mount points.
  • The tools fence is not active in the replay guests, so OpenCode and its tools share one cgroup set.
