# Limit study: perfect L2 and perfect TLB

The `--perfect-l2` model is built and validated. The sweep (1B detailed
instructions per agentic window, `COMPRESS_STATS=1`) is planned (below). On
one 5M-instruction jq-2598 window, IPC goes from 0.760 to 1.088. That is a
smoke-test number, not a result.

## Question

How much do misses beyond the L2 cost the agentic workloads? A perfect L2
always hits at its normal hit latency, cold misses included. That makes it
an upper bound for anything below the L2 (bigger L2, an L3, better L2
prefetching, faster DRAM). It complements the capacity runs of
[[2026-10-23-rubocop-15g-cache-btb-tlb]], which keep cold misses.

## Model

`--perfect-l2` (`sim_opts.py`, `cache_hierarchy.py`; switch table in
[[neoverse-v2]]):

- **No L2 and no per-core L2 crossbar.** The L1I, L1D and MMU cache
  connect straight to the memory bus.
- **The memory bus has the L2 crossbar's timing:** `L2XBar` width (32 B)
  and latencies (frontend 1, forward 0, response 1).
- **Memory is a `SimpleMemory`** with latency `--perfect-l2-cycles`
  (default 11, `max(tag, data)` of the `L2` class, which is the L2 hit cost
  with `sequential_access` off). The latency is a whole number of clock
  periods (3663 ps at 3 GHz). There is no variation, and the bandwidth is
  1 TiB/s.

An L1 miss then takes the same path as a baseline L2 hit: L1 lookup,
1-cycle crossbar, 11 cycles, crossbar response, L1 fill.

**Why `SimpleMemory`.** The DRAM model cannot give a flat latency. It adds
the controller's frontend and backend latency, row hits and misses, bank
conflicts, refresh and queuing. `SimpleMemory` is a store with one fixed
latency.

**Why not keep the L2 in front of a zero-latency memory.** An L2 miss
would still cost the forward lookup (11 cycles), the memory-bus
latencies, and the L2 fill (`response_latency` 11). That is about
30 cycles, not 11.

**What is lost.** There are no L2 statistics, so the run cannot say how
many accesses would have missed the L2; the paired baseline can. The L2
BOP prefetcher goes away with the L2.

> [!warning] Shared-crossbar topology panics
> The first version kept the per-core L2 crossbar and connected it to the
> memory bus. Warm-up then panicked in `snoop_filter.cc:122` ("double
> request"). The memory bus's snoop filter tracks lines per port. With no
> cache below the shared crossbar, an L1I and an L1D miss to the same line
> look like two requests from one port. gem5's `PrivateL1CacheHierarchy`
> connects each L1 to the memory bus for the same reason.

## Validation (2026-11-02)

Run: jq-2598, 2M warm-up and 5M detailed instructions in 1M blocks.
Baseline, perfect and a perfect repeat, `runs/perfect-l2/validate.sh`; the
readout is `runs/perfect-l2/compare.py`. One window only.

| | baseline | perfect | perfect repeat |
|---|---|---|---|
| IPC | 0.7597 | 1.0879 | 1.0879 |
| L1I avg MSHR miss latency (cycles) | 84.7 | 19.8 | 19.8 |
| L1D avg MSHR miss latency (cycles) | 83.8 | 21.3 | 21.3 |
| MMU cache avg MSHR miss latency (cycles) | 65.9 | 17.2 | 17.2 |
| L1D demand misses | 75,771 | 92,274 | 92,274 |
| L1D MSHR hits | 45,826 | 58,749 | 58,749 |

- **Restore:** the checkpoint restores into `SimpleMemory`, with the
  switch from atomic to detailed and the warm-up as usual.
- **Determinism:** the two perfect runs match on every number above and
  on the cycle count.
- **Latency:** an L1 miss takes about 17–21 cycles. The expected
  contention-free path is the L1 tag latency (MMU 1, L1I 2, L1D 4) plus
  1 + 11 + 1, plus 2 cycles to move a 64-byte line over the 32-byte bus.
  That gives about 16, 17 and 19 cycles, and the measured averages sit
  0.8–2.3 cycles above. Likely bus queuing; not verified.
- **More L1D misses in the perfect run:** most of the increase is MSHR
  hits (+12.9k of +16.5k), meaning secondary misses to lines already in
  flight. Interpretation, not verified: the faster core has more loads in
  flight to the same lines.

The baseline has no separate statistic for L1 misses that hit the L2, so
the equality with a baseline L2 hit rests on the matching path, not on a
measurement.

## Perfect TLB

`--perfect-tlb` (`ArmMMU.perfect_tlb`, `src/arch/arm/mmu.cc` `MMU::getTE`)
makes every translation of the O3 core hit. On a TLB miss in a timing
translation, the MMU runs the table walk **functionally** (the walker's
functional walk unit, descriptors read with `sendFunctional`) instead of
timed. The walk fills the L1 and L2 TLBs as a timed walk would, and the
translation finishes inside `translateTiming`, like a hit. Each such walk
counts in `mmu.perfectWalks`.

- **Same entry or fault as a timed walk.** gem5 does not implement
  hardware Access/Dirty flag updates (FEAT_HAFDBS), so walks never write
  descriptors, and the functional walk runs the same descriptor code.
  Functional reads see the newest copy of a descriptor in the caches.
- **What it removes beyond [[infinite-l2-tlb]]:** compulsory misses and
  misses after a `TLBI`, besides capacity and conflict misses. L2 TLB
  hits are already free ([[tlb-hierarchy]]), so nothing else changes.
- **Prefetch translations still drop on a miss** (`PrefetchTLBMiss`, before
  the walk). Decided with the user so the TLB effect stays separate from
  FDP reach.
- **Atomic translations are untouched**: the restore and the atomic
  phases go through `translateAtomic`; only the O3 core gets the switch.
- **Wrong-path translations also finish at once**, so wrong-path loads can
  reach the caches sooner than they would behind a walk.
- Exclusive with `--infinite-tlb`. Banner: `L2TLB=perfect`.

### Validation (2026-11-02)

Same jq-2598 window (2M warm-up, 5M detailed, 1M blocks),
`runs/perfect-l2/validate-tlb.sh`, readout
`runs/perfect-l2/compare_tlb.py`. One window only: smoke-test numbers.

| | baseline | perfect TLB | perfect TLB repeat | perfect TLB + L2 | perfect L2 |
|---|---|---|---|---|---|
| IPC | 0.7597 | 0.7791 | 0.7791 | 1.1051 | 1.0879 |
| walk requests (`walker.walks`) | 22,775 | 14,542 | 14,542 | 11,627 | 20,776 |
| … of which `perfectWalks` | 0 | 14,542 | 14,542 | 11,627 | 0 |
| completed walks (TLB fills) | 5,745 | 5,599 | 5,599 | 5,419 | 5,529 |
| walk squashed before starting | 10,184 | 0 | 0 | 0 | |
| MMU cache accesses | 16,646 | 0 | 0 | 0 | 14,615 |
| L1 iTLB / dTLB misses | 340k / 35.9k | 393k / 26.2k | same | 221k / 28.0k | 231k / 37.4k |
| prefetch translations dropped | 314,632 | 366,977 | same | 197,800 | 209,776 |

- **Switch off is a no-op:** the baseline on the new binary matches the
  earlier baseline (`validate/baseline`) on every statistic except the
  new `perfectWalks` line (0) and host timing.
- **Determinism:** the two perfect-TLB runs match on every number.
- **No timed walks:** every walk request is a perfect walk, the MMU cache
  sees no accesses, and nothing is squashed.
- **Walks that do not fill the TLB:** 8,943 of the 14,542 perfect walks
  end without an insert, presumably in a translation fault (wrong-path
  accesses to unmapped addresses; such a fault repeats on every miss).
  Not verified per walk. The baseline shows the same pattern: 22,775
  requests, 5,745 completed, 10,184 squashed.
- **Effect on this window:** +2.6% IPC from the TLB alone, +45% with the
  perfect L2 (vs +43% for the perfect L2 alone).
- **Open:** more iTLB misses and dropped prefetch translations with the
  perfect TLB (+53k each). FDP runs further ahead when the front end does
  not wait on walks; not checked.

## Planned sweep

Nine agentic-only smart sweeps, `runs/sweep/<stamp>-<name>`: 27 tasks each, 1B detailed
instructions after 20M of warm-up, 200K blocks, `COMPRESS_STATS=1`, first
launched at commit `f15bdb37f0`. Launcher and comparisons: `runs/perfect-sweep/launch.sh`,
`compare.sh`.

| sweep | flags | compared against |
|---|---|---|
| `base` | none | |
| `nofdp` | `--disable-fdp` | `base` |
| `ptlb` | `--perfect-tlb` | `base` |
| `pl1i` | `--perfect-l1i` | `base` |
| `pl1i-ptlb` | `--perfect-l1i --perfect-tlb` | `base` |
| `pl2` | `--perfect-l2` | `base` |
| `pl2-ptlb` | `--perfect-l2 --perfect-tlb` | `base` |
| `pl2-nofdp` | `--perfect-l2 --disable-fdp` | `nofdp` |
| `pl2-nofdp-ptlb` | `--perfect-l2 --disable-fdp --perfect-tlb` | `nofdp` |

- **Launch order:** `base`, `pl2` and `pl1i` first; the other six start
  once those three have launched all their runs.
- **"FDP off" here is `--disable-fdp`**, which turns off the whole decoupled
  front end, as in [[2026-10-14-fdp-off-sweep]]. `--perfect-l1i` only
  detaches the FDP prefetcher.

A first launch (2026-11-03) was stopped after about 40 minutes, with no
run finished, and its directories deleted. The sweep waits for top-down
counters, to be added to gem5 in a separate piece of work, so the results
can be analysed with them.
