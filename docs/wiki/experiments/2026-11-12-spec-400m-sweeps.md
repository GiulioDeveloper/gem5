# SPEC at 400M: the agentic limit-study configurations

SPEC counterparts of every agentic 1B limit-study and front-end sweep:
16 configurations × 26 SPEC SimPoint checkpoints × 400M detailed
instructions. They are needed because only the front-end sweeps had SPEC
runs (at 200M), so suite comparisons of the perfect L1D, L2 and TLB rested
on top-down shares, which misjudge memory cost
([[2026-11-12-miss-count-vs-miss-cost#Top-down memory-bound vs the cycles a perfect L1D saves]]).
Status: sweeps launched 2026-11-12 17:20 (stamp `20261112-1720`, commit
`387f75040f`); all sixteen finished 2026-11-13, 26/26 runs each. **First result: SPEC gains as much
from a perfect L1D as agentic (+47% vs +43% geomean)**, and top-down
memory-bound underestimates it in both suites.

## Question

Does SPEC gain from a perfect L1D, L2, L1I or TLB, from FDP and from the
wider, faster front end as much as agentic does
([[2026-11-06-perfect-l1d]], [[2026-11-02-perfect-l2]],
[[2026-11-03-perfect-l1i]], [[2026-11-05-front-end-width]])? In
particular, is SPEC's top-down memory-bound share as far below its
perfect-L1D saving as agentic's (39% of the saving)?

## Setup

`runs/spec-400m/launch.sh`: 16 smart sweeps
`runs/sweep/<stamp>-spec4-<name>`, `SPEC_DET=400000000`, 20M warm-up,
200K blocks, `SETTLE=1`, `COMPRESS_STATS=1`. All configurations at one
window length, so each has a SPEC baseline (`spec4-base`) of the same
length; the older 200M SPEC sweeps are not mixed in.

- **Concurrency:** the first six sweeps start at once with 4 runs each;
  each later sweep (2 runs) starts when the host runs at most 22 gem5
  processes, so about 24 run at once on the 32-thread host (8 P-cores, 16
  E-cores). Memory is gated by `smart_sweep.sh`.
- **Cost estimate:** a 200M SPEC run took 0.31 h of host time (median,
  `20261105-1143-spec-fe6`), so about 0.7 h at 400M: about 300 run-hours,
  roughly 13-16 h wall. Actual: slower, about 2 h per run for the
  later sweeps (24 runs at once, launches held by the memory gate at
  times overnight); the last ten sweeps should end on the evening of
  2026-11-13 (an estimate).
- **Window length:** 400M runs past the 200M used so far from each
  SimPoint checkpoint; whether the second half is as representative of
  the benchmark as the first is not checked.
- Not included: the October infinite-BTB / infinite-TLB sweeps
  ([[2026-10-16-btb-tlb-limit-study]]), which used different settings.

## Smoke test (2026-11-12)

`runs/spec-400m/smoke.sh`: lbm, fotonik3d, cactus and omnetpp × base,
pl1d, pl2, ptlb, pl1d-pl1i; 2M warm-up + 5M detailed; readout
`smoke_readout.py`. One short window each: a functional check, not a
result.

| benchmark | pl1d | pl2 | ptlb | pl1d-pl1i |
|---|---|---|---|---|
| 709.cactus_r | +603% | +448% | +1.0% | +603% |
| 710.omnetpp_r | +72% | +2.4% | +0.1% | +72% |
| 749.fotonik3d_r | +576% | +336% | +0.2% | +585% |
| 782.lbm_r | +96% | +88% | +0.1% | +96% |

- All 20 runs finish with exit 0; no panic or fatal; the warnings are
  the same as in the base runs.
- **No SVE masked stores** on these four (`perfectDCacheMaskedWrites`
  0), no atomics except 7 on fotonik3d; timed bypasses only exclusives
  (46 on fotonik3d).
- Under the perfect L1D the L1D sees no demand access, and the L2 sees at
  most 991 demand accesses (walker and exclusives); under the perfect L2
  it sees none.
- omnetpp gains +72% from a perfect L1D but only +2.4% from a perfect
  L2: its misses hit in the L2 (28-cycle primary latency,
  [[2026-11-12-miss-count-vs-miss-cost]]), so it pays the L2 hit
  latency, which a perfect L2 keeps.
- The first attempt passed the arguments wrong (`xargs -L1` joins a line
  ending in a blank to the next); those runs were stopped and deleted.

### First six configurations (complete 2026-11-13 morning)

`base`, `pl1d`, `nofdp`, `pl1i`, `pl2` and `ptlb` finished, 26/26 each,
no failures; the other ten were about half done at 09:30. Geometric-mean
IPC ratio against `spec4-base` (`summary/sweep.csv` of each sweep),
beside the agentic 1B result against its `base`:
Both suites on one page: `runs/sweep/20261112-1720-compare-5cfg/compare.html`
(`runs/spec-400m/compare.sh`, which merges each configuration's agentic
and SPEC sweeps; rerun it with `all` when the other ten finish).

| config | SPEC geomean | SPEC min / median / max | agentic geomean |
|---|---|---|---|
| perfect L1D | **1.466** | 0.983 / 1.250 / 5.575 | **1.432** |
| perfect L2 | 1.374 | 0.981 / 1.175 / 4.719 | 1.482 |
| perfect L1I | 1.015 | 0.996 / 1.002 / 1.238 | 1.096 |
| perfect TLB | 1.005 | 0.977 / 1.000 / 1.042 | 1.043 |
| FDP off | 0.973 | 0.811 / 0.998 / 1.002 | 0.968 |

- **SPEC gains as much from a perfect L1D as agentic** (+46.6% vs
  +43.2% geomean), with a different shape. SPEC is a long tail:
  cactus +458%, fotonik3d +264%, vpr +138%, cppcheck +126%, lbm and roms
  about +104%; ten benchmarks under +10%, median +25%. Agentic is
  uniform: most tasks +45% to +58%.
- **714.cpython_r is 1.7% slower with a perfect L1D.** Not explained; to
  check (a timing artifact of the functional path, or a wrong-path
  effect).
- **FDP off: the median is unchanged, but the geomean falls by 2.7%,**
  driven by large-code benchmarks (minimum 0.811); it matches agentic's
  −3.2%.
- The front-end limits (perfect L1I, perfect TLB) still separate the
  suites; the data side does not.

Cycles saved by the perfect L1D, by top-down category (cycle-equivalents
per 1,000 instructions, mean over 26 benchmarks, total 257), beside
agentic's (total 310):

| category | SPEC | agentic |
|---|---|---|
| back end: memory | 51% | 39% |
| back end: core | 36% | 37% |
| front end | 9% | 15% |
| bad speculation | 3% | 3% |
| back end: serialize | 0% | 7% |

- Taking memory-bound at face value predicts +17.4% for SPEC (geomean of
  1/(1 − memory-bound)); measured +46.6%. **Top-down memory-bound
  underestimates SPEC's memory cost too,** by a little less than
  agentic's (+13.8% predicted, +43.2% measured). Core bound holds about a
  third of the saving in both suites.
- Caveat: SPEC is at 400M and agentic at 1B; different window lengths.
