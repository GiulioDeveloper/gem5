# Limit study: perfect L1D

The `--perfect-l1d` model is built and validated on one 5M-instruction
jq-2598 window: IPC goes from 0.760 to 1.032 (+35.9%). O3's LSQ serves
plain cacheable loads, stores and atomic operations with functional
accesses answered after the 4-cycle L1D hit latency, mirroring
[[2026-11-03-perfect-l1i]]. The real L1D stays in place for exclusives,
MMIO and cache maintenance. One window only; no sweep yet.

## Question

How much do L1D misses cost the agentic workloads? This is the data-side
counterpart of the perfect L1I, L2 and TLB limit studies
([[2026-11-03-perfect-l1i]], [[2026-11-02-perfect-l2]]).

## Setup

Switches: `--perfect-l1d` and `--perfect-l1d-cycles N` (`sim_opts.py`;
O3 params `perfectDCache`, `perfectDCacheLatency`). The default N is
`max(tag_latency, data_latency)` of `L1D`, which is 4. The flag also
detaches the L1D prefetcher and shows in the banner. The
functional-access background is on [[functional-access]].

### As built (2026-11-06)

- `LSQUnit::trySendPacket` asks `LSQ::perfectDCacheBypass` whether a
  packet can be served functionally; if so, `LSQ::sendPerfectDCacheAccess`
  accesses it now and schedules the response at `clockEdge(N)` into
  `LSQ::recvTimingResp`. The response skips the dcache port's throttling
  and port stats (throttling is off in our configs). Port limits
  (`cachePortAvailable`) and `cacheBlocked` still gate both paths.
- **Served functionally:** `ReadReq`, software prefetches, `WriteReq`,
  and atomics with an operation functor (Arm LSE, `SWP`, `CAS`).
  Functional accesses do not apply atomic operations, so the LSQ does it
  as a cache hit does: functional read, return the old value, apply the
  functor, functional write. Safe because O3 issues atomics at the ROB
  head.
- **Timed through the real L1D**, counted by reason in
  `lsq0.perfectDCacheBypasses`: exclusives, atomics without a functor and
  locked RMW, uncacheable/strictly ordered, cache maintenance, addresses
  outside memory, HTM and any other command.
- **Masked writes:** served functionally; the first gap is fixed in
  `Packet::trySatisfyFunctional` (only enabled bytes are copied). The
  second gap is unreachable here (no plain store stays timed), so it is
  left as upstream's `warn`. Counted in `perfectDCacheMaskedWrites`; zero
  on the agentic restores (no SVE).
- `LSQ::isDrained` waits for responses in flight. Stats:
  `perfectDCacheAccesses`, `perfectDCacheAtomics`,
  `perfectDCacheMaskedWrites`, `perfectDCacheBypasses`.
- Functional writes do not clear the cache-side exclusive monitor
  (`CacheBlk` locks). Harmless on one core: whether a store from the same
  PE clears the monitor is implementation defined.

### Design options

| option | how | verdict |
|---|---|---|
| **LSQ goes functional** | in `LSQUnit::trySendPacket`, cacheable loads and stores use `dcachePort->sendFunctional` and complete after N cycles | **recommended** |
| new `PerfectCache` SimObject | a stateless object in place of the L1D: it serves requests functionally and never fills | viable; worth it only as a reusable component (it could also replace the `--perfect-l1i` hack in `fetch.cc`) |
| copy `Cache` and fill misses functionally | an always-hit cache that fills lines functionally on a miss | rejected: breaks the snoop filters |
| huge L1D (config only) | the `--cache-scale` mechanism, applied to the L1D alone | a bound only: compulsory misses remain, and a large tag array costs host memory |

**Recommended model, LSQ functional.**

- **Functional:** cacheable loads and stores. The data is read or written
  when the request is sent, as a timed hit is handled when it arrives,
  and the response comes back after N cycles.
- **Timed through the real L1D:** exclusives (LL/SC), atomics, uncacheable
  and strictly-ordered accesses, cache maintenance, and the TLBI-sync
  packet.
- **Kept:** L1D port limits (`cachePortAvailable`), store-to-load
  forwarding, and snoops to the LSQ, which still arrive through the real
  L1D.
- **Correctness of mixing the two paths.** A store-exclusive or atomic is
  non-speculative, so no younger store is written back while one is in
  flight. No plain store stays timed. So the second masked-write gap
  ([[functional-access#Masked writes]]) cannot occur.
- **Masked stores** are split into unmasked functional writes, or the
  first gap is patched in `Packet::trySatisfyFunctional`. Turn the
  second gap's `warn` into a `panic` under the perfect L1D as a guard.
- **Also:** detach the L1D prefetcher (Stride+SMS), make `isDrained` wait
  for accesses in flight, add stats (functional accesses, timed
  fallbacks by reason, masked splits), and a banner fragment.
- **No data traffic in the hierarchy:** the L2 sees no data accesses. As
  with `--perfect-l1i`, the gain mixes the L1D gain with the L2 having
  all its capacity and bandwidth for instructions.

**PerfectCache: what it would have to reimplement.**

- the store-exclusive result (`setExtraData`);
- atomics (functional read, apply the functor, functional write);
- forwarding MMIO timed, with retry;
- cache maintenance;
- `recvAtomic` for the atomic warm-up core;
- drain, and snoop forwarding or a decision to drop snoops.

Every one of these is a new chance to be subtly wrong. Its gains:
it works with any CPU, it can handle masked writes inside the object, and
as the L1I it should reproduce `--perfect-l1i` bit for bit. It would not
replace `--perfect-l2`: that is a coherence responder, which the existing
`SimpleMemory` already handles correctly.

**Why a hacked `Cache` fails.** A line filled functionally never passes
through the `L2XBar`/`SystemXBar` snoop filters.

- When the line is later evicted, `SnoopFilter` panics ("requestor ... is
  not a holder").
- Virtio DMA snoops never reach the line, so the guest reads stale I/O
  buffers.
- It gives no simulation speedup either.

**Simulation speed (not measured).** The LSQ and PerfectCache options
remove L1D misses and their L2 and DRAM events. But every access then
walks the hierarchy functionally. The net is expected to be positive;
measure it on the validation window.

## Validation (2026-11-06)

Run: jq-2598, 2M warm-up and 5M detailed instructions in 1M blocks.
Baseline, perfect and a perfect repeat, `runs/perfect-l1d/validate.sh`;
readout `runs/perfect-l1d/compare.py`.

| | baseline | perfect L1D | perfect repeat |
|---|---|---|---|
| IPC | 0.7597 | 1.0322 | 1.0322 |
| `perfectDCacheAccesses` | 0 | 1,973,577 | 1,973,577 |
| of which atomics | 0 | 33,950 | 33,950 |
| timed bypasses | 0 | 41 (all exclusives) | 41 |
| L1D demand accesses / misses | 1,954,127 / 75,771 | 0 / 0 | 0 / 0 |
| L2 demand accesses | 154,215 | 89,386 | 89,386 |
| L1I avg MSHR miss latency (cycles) | 84.7 | 62.7 | 62.7 |
| host time | 26 s | 25 s | 25 s |

- **Switch off is a no-op:** the baseline equals the perfect-L1I baseline
  (`runs/perfect-l1i/validate/baseline`) on every number shown.
- **Determinism:** the two perfect runs match on every number.
- **No data traffic:** the L1D sees no demand access and issues no
  prefetch. The L2 sees 42% fewer accesses; the L1I miss latency falls
  from 84.7 to 62.7 cycles. That instruction-side gain is mixed into the
  +35.9%, as the data side was in the perfect-L1I gain.
- **Guest sanity:** the same processes exit with code 0 in both runs and
  the console shows no oops. Scheduling differs (timing changes when
  timer interrupts land), so the task traces are not comparable event by
  event.
- **First build left atomics timed** (`runs/perfect-l1d/validate-v1`):
  34K LSE atomics in 5M instructions (one per ~150) went to an L1D that
  plain stores no longer filled, and missed more than in the baseline
  (3,747 vs 1,673 misses). IPC was 0.985. Serving them functionally fixed
  it: +35.9% instead of +29.7%.
- **Host speed:** unchanged on this window (25 vs 26 s).

**Stress checks** (`runs/perfect-l1d/stress.sh`, same checkpoint):

- **50M-instruction window, `--perfect-l1d`:** completes, IPC 1.422,
  16.8M functional accesses including 120,603 atomics; 170 timed
  bypasses, all exclusives; zero L1D accesses. Ten guest processes exit
  with code 0; no oops, no panic, no masked-write warning. No baseline was run for
  this window, so the IPC has no comparison yet.
- **5M window, `--perfect-l1i --perfect-l1d`:** completes, IPC 1.135
  (baseline 0.760). Neither L1 sees an access. The L2 still sees 3,818
  accesses, which are the table walker and the exclusives. The banner
  shows both switches.

## Sweep

after 20M of warm-up, 200K blocks, `COMPRESS_STATS=1`. These are the
settings of the perfect L1I/L2/TLB sweeps, so the comparison uses their
sweeps (`runs/sweep/20261104-1115-*`, commit `5889fe1205`). Launcher,
status and comparison: `runs/perfect-l1d/launch.sh`, `status.sh`,

| sweep | flags | compared against |
|---|---|---|

### Execution check (2026-11-07)

Does the guest run the same work under the perfect L1D? All 27 tasks per
sweep against the 11-04 `base`, with `pl1i` and `ptlb` (validated
earlier) as the spread a timing change normally causes;
`runs/perfect-l1d/check_exec.py`.

- **Same work, further along.** Instruction share by process overlaps
  base by 95.9% on average for `pl1d` (85-100% per task), vs 98.5% for
  `pl1i`. The shifts are the faster core reaching later steps of the
  agent's script in the same 1B instructions: php-cs-fixer reaches a
  `php` run base never starts, fmt-3750 and docusaurus run more `git`,
  and `docker` shrinks. The larger drift matches the larger speedup.
- **Tool calls in the same order** on every task (`analysis/tools.csv`);
  the perfect-L1D runs often reach one more call. The two apparent
  mismatches are a call id the tracer read as garbage in both runs
  (fmt-3750) and an input base had not logged yet (jekyll-8167).
- **Exit codes:** the only extra non-zero exits are `false` (81 vs 63
  in base), a polling loop that iterates more when the guest is faster.
  `git` (3) and `timeout` (2) failures are identical. No console oops.
- **Instruction mix:** stores per 1000 instructions 150.4 → 153.8,
  branches 201.2 → 203.9, loads 219.1 → 220.3, user share 79.9 → 80.2%;
  per-task changes up to +21 stores/kinst, on the tasks whose process
  mix shifts most. Consistent with the mix shift, not with corrupted
  data: a broken load or atomic would show up as crashes, hangs or
  diverging tool calls.

## Results

All 81 runs finished (2026-11-07), none failed. Readout:
`runs/sweep/20261106-2004-compare/` (`runs/perfect-l1d/compare.sh`).
Geometric-mean IPC ratio over the 27 agentic tasks, against the 11-04
`base` (geomean IPC 1.009):

| sweep | IPC ratio | product of the parts |
|---|---|---|
| `pl1d` | 1.432 | |
| `pl1i` (11-04) | 1.096 | |
| `ptlb` (11-04) | 1.043 | |
| `pl1d-pl1i` | 1.588 | 1.569 |
| `pl1d-ptlb` | 1.488 | 1.494 |

- A perfect L1D is worth about 4.5× a perfect L1I and 10× a perfect TLB
  on these windows. Per task (23 tasks read out early): +8.7% (preact)
  to +67% (fmt-3750), most between +45% and +58%; above `pl1i` on every
  task.
- L1D and L1I gains combine slightly better than multiplicatively,
  consistent with each freeing L2 bandwidth for the other; the TLB gain
  just multiplies. Small effects, one sweep each.
- These are upper bounds: the model also removes the data traffic from
  the L2 (see Setup).

## Conclusions

None yet.

## Decisions

- 2026-11-06: build the LSQ-functional model (the user chose it). It is
  the smallest change, and every rare access stays on a tested path.
- 2026-11-06: serve atomics with a functor functionally too; leaving them
  timed made them miss more than in the baseline.
