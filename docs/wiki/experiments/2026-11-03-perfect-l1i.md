# Limit study: perfect L1I

The `--perfect-l1i` model is built and validated. The sweep is running (below). On
one 5M-instruction jq-2598 window, IPC goes from 0.760 to 0.845 (+11.2%).
That is a smoke-test number, not a result.

## Question

How much do L1I misses cost the agentic workloads? A perfect L1I always
hits at its normal hit latency, cold misses included. It is one piece of
the front-end upper bound; the others are the BTB
([[2026-10-16-btb-tlb-limit-study]]) and the ITLB (`--perfect-tlb`,
[[2026-11-02-perfect-l2]]).

## Model

`--perfect-l1i` (`--perfect-l1i-cycles N`, default 2) sets the O3 params
`perfectICache` and `perfectICacheLatency`. In `Fetch::finishTranslation`,
`sendPerfectICacheRead` replaces `icachePort.sendTimingReq`:

- **Functional read, timed delivery.** The fetch block is read with
  `sendFunctional` on the I-cache port. An auto-deleting event delivers it
  to `processCacheCompletion` N cycles later. Fetch goes through the same
  `IcacheWaitResponse` state as with a timed hit. Each read is counted in
  `fetch.perfectICacheReads`.
- **N = the L1I hit latency.** A timed hit responds at
  `clockEdge(max(tag_latency, data_latency))` (`BaseCache::
  calculateAccessLatency`, `sequential_access` off), which is 2 cycles for
  `L1I`. The default reads it from the `L1I` class.
- **Correct code under JIT.** A functional read snoops every cache, so code
  that is still dirty in the L1D is fetched correctly.
- **Squashes and drain.** A read squashed in flight is dropped by the
  existing `pkt->req != memReq` check (`fetch.icacheSquashes`).
  `Fetch::isDrained` waits until no perfect read is in flight, so the CPU
  cannot switch out while one is pending.
- **The ITLB is untouched.** Translation still runs timed.

**The hierarchy sees no instruction traffic.** This was the user's choice,
for simplicity. The L1I gets no accesses. The L2 holds no instruction
lines and spends no bandwidth or MSHRs on them, so **data gets all of the
L2's capacity and bandwidth**. The speedup therefore mixes the front-end
gain with a data-side gain. The FDP prefetcher is detached because it
issues from FTQ inserts and would keep pushing instruction lines into the
L2. The decoupled front end stays on, unlike with `--disable-fdp`. The
tagged L1I prefetcher stays attached but never fires. Banner:
`L1I perfect (2 cyc)`, `FDP=off`.

**Option not built: a shadow request.** Fetch would still send the timed
request, keeping the L1I/L2 state and traffic as in the baseline, but would
not wait for it. That would separate the front-end gain from the L2
relief. Set aside for simplicity.

## Validation (2026-11-03)

Run: jq-2598, 2M warm-up and 5M detailed instructions in 1M blocks.
Baseline, perfect and a perfect repeat, `runs/perfect-l1i/validate.sh`; the
readout is `runs/perfect-l1i/compare.py`. One window only.

| | baseline | perfect L1I | perfect repeat |
|---|---|---|---|
| IPC | 0.7597 | 0.8448 | 0.8448 |
| fetch lines (`fetch.cacheLines`) | 1,187,942 | 1,201,748 | 1,201,748 |
| `perfectICacheReads` | 0 | 1,201,748 | 1,201,748 |
| L1I demand accesses / misses | 1,187,935 / 12,494 | 0 / 0 | 0 / 0 |
| fetch cycles in `icacheWaitResponse` | 1,412,435 | 1,239,752 | 1,239,752 |
| L2 demand accesses | 154,215 | 68,416 | 68,416 |
| L1D avg MSHR miss latency (cycles) | 83.8 | 75.1 | 75.1 |

- **Switch off is a no-op:** the baseline matches the perfect-L2 baseline
  (`runs/perfect-l2/validate/baseline`) on IPC and L1D misses.
- **Determinism:** the two perfect runs match on every number.
- **No instruction traffic:** every fetch line is a perfect read; the L1I
  sees no access and issues no prefetch.
- **The L2 sees 56% fewer accesses,** and the L1D miss latency falls from
  83.8 to 75.1 cycles. That is the data-side gain mixed into the +11.2%.
  How much of the gain it accounts for is not measured.
- **Fetch still waits about one cycle per line.** `icacheWaitResponse`
  drops by only 12% (1.41M to 1.24M cycles), about 1.03 cycles per fetch
  line with the perfect L1I. Most of the baseline's wait is the 2-cycle
  hit, not misses. The cause is in the code: fetch holds one 64-byte fetch
  buffer and has at most one I-cache request in flight per thread. The
  early ("pipelined") request is issued only when fetch crosses into the
  next line, and not while a request is pending (`issuePipelinedIfetch`,
  `fetch.cc`). That request goes out in the cycle that finishes the
  current line, which hides one cycle of the hit latency but gives no
  lookahead. So each new line, sequential or after a taken branch, waits
  for the hit latency minus one cycle (one cycle at 2-cycle hits) even
  when the hit is guaranteed. With 1-cycle reads the wait disappears
  (I-cache wait 12.7% → 0.0% of cycles on cppcheck and 14.5% → 0.6% on
  rubocop, [[2026-11-03-top-down-validation]]). A real decoupled front
  end reads the I-cache for upcoming fetch targets ahead of time, so it
  probably does not have this per-line bubble. Waiting cycles are
  not necessarily lost cycles: the 32-µop fetch queue can hide them from
  decode. **Their IPC cost is 3-6%** (2026-11-05, the 400M windows of
  [[2026-11-03-top-down-validation]], perfect L1I at 2 vs 1 cycle):
  rubocop-13560 1.064 → 1.096 (+3.0%), 727.cppcheck_r 0.960 → 1.019
  (+6.1%). Front-end bound falls by 8 points of slots, but only about a
  third of the freed slots become saved cycles: per 1000 µops, rubocop's
  front-end slots drop 612 (76 cycles' worth) while cycles drop 26 and
  back-end bound slots rise 318; cppcheck: −910 slots, −52 cycles, +490
  back-end slots. The back end is the next limit. Two windows only; the
  1-cycle read stands for an ideally pipelined I-cache with lookahead.

## Sweep

Nine agentic-only smart sweeps, `runs/sweep/<stamp>-<name>`: 27 tasks each, 1B detailed
instructions after 20M of warm-up, 200K blocks, `COMPRESS_STATS=1`, first
launched at commit `f15bdb37f0`. Launcher and comparisons: `runs/perfect-sweep/launch.sh`,
`compare.sh`.

| sweep | flags | compared against |
|---|---|---|
| `base` | none | |
| `nofdp` | `--disable-fdp` | `base` |
| `ptlb` | `--perfect-tlb` | `base` |
| `pl1i` | `--perfect-l1i` | `base` |
| `pl1i-ptlb` | `--perfect-l1i --perfect-tlb` | `base` |
| `pl2` | `--perfect-l2` | `base` |
| `pl2-ptlb` | `--perfect-l2 --perfect-tlb` | `base` |
| `pl2-nofdp` | `--perfect-l2 --disable-fdp` | `nofdp` |
| `pl2-nofdp-ptlb` | `--perfect-l2 --disable-fdp --perfect-tlb` | `nofdp` |

- **Launch order:** `base`, `pl2` and `pl1i` first; the other six start
  once those three have launched all their runs.
- **"FDP off" here is `--disable-fdp`**, which turns off the whole decoupled
  front end, as in [[2026-10-14-fdp-off-sweep]]. `--perfect-l1i` only
  detaches the FDP prefetcher.

A first launch (2026-11-03) was stopped after about 40 minutes, with no
run finished, and its directories deleted, to wait for the top-down
counters. The sweep was relaunched on 2026-11-04 at commit `5889fe1205`
(top-down accounting merged; the counters are experimental and change no
simulated stat), as `runs/sweep/20261104-1115-*`. A 1B run simulates at
about 200 KIPS, so about 1.4 h; the whole sweep should take about two
days.

## How much of the L2 holds instructions (2026-11-09)

An estimate of the L2 room that `--perfect-l1i` hands to data. Source:
the L2's `tags.occupancies::<requestor>`, the time-weighted count of valid
lines by the requestor that allocated each (`BaseTags::insertBlock`), reset
every stats block. Weighted by block time over each 1B window, median over
the 27 agentic checkpoints (`runs/l2-occupancy/l2_split.py`, `l2_mix.py`;
per checkpoint in `l2_split.csv`):

| sweep | instruction (L1I demand + L1I prefetchers) | data (L1D demand + prefetchers) | walker | writebacks (mixed) | L2 BOP (mixed) |
|---|---|---|---|---|---|
| base | 28.4% (16–44%) | 27.5% | 1.9% | 6.0% | 35.0% |
| nofdp | 3.5% | 29.2% | 2.1% | 6.4% | 46.6% (11% of lines invalid) |
| pl1i | 0 | 42.4% | 2.9% | 8.2% | 44.3% |
| pl1d | 78.7% | 0 | 5.1% | 0.7% | 14.9% |

- **Instruction lines are at least 28% of the base L2,** and most come from
  FDP (20.4% FDP, 5.2% tagged L1I prefetcher, 2.4% demand). Without FDP
  they fall to 3.5%.
- **Two classes are mixed and can't be split from the stats.** One is
  writebacks: L1I clean evictions (`writeback_clean`) and L1D evictions
  share the `writebacks` requestor and reallocate after an L2 eviction
  (`mostly_incl`). The other is BOP prefetches, trained on all L2 traffic.
  So the base instruction share is **between 28% and 69%**. Sharing the
  mixed part by the instruction fraction of L2 read requests (ReadCleanReq,
  median 46%) gives about **45%**. That proxy is rough: FDP's own requests
  are ReadCleanReq.
- Under pl1i the data share grows from 27.5% to 42.4% and BOP's from 35% to
  44%: the room freed by instructions goes to data and to BOP.
- An exact split needs instrumentation: a writeback requestor per L1, and
  BOP prefetches tagged by the class of their triggering access.

## Width 8 and a 1-cycle perfect L1I (2026-11-09)

**Question:** is the +9.6% of `--perfect-l1i` held back by something
else in the front end? Two suspects: the 6-micro-op fetch and decode
width ([[2026-11-05-front-end-width]]), and the fetch wait at every new
cache line, which a 2-cycle perfect L1I keeps.

**Sweep:** `runs/sweep/20261109-1619-fe8-pl1i1`, `--front-end-width 8
--perfect-l1i --perfect-l1i-cycles 1`, 27 agentic tasks, 1B windows, same
settings as the sweep above (`runs/fe8-pl1i/launch.sh`). Commit
`b4f8943064` (perfect L1D added; a no-op with the switch off).

**Baselines:** `20261104-1115-base` (width 6), `20261105-1143-fe8`
(width 8, L1I real) and `20261104-1115-pl1i` (width 6, perfect L1I at 2
cycles). Not separable from this sweep alone: width 8 at 2 cycles, and 1
cycle at width 6.

**SPEC counterpart:** `runs/sweep/20261109-1619-spec-fe8-pl1i1`, the same
flags on 26 SPEC checkpoints × 200M (`runs/fe8-pl1i/launch-spec.sh`), against
`20261105-1143-spec-fe6` and `spec-fe8`. No SPEC sweep with `--perfect-l1i`
alone exists, so on SPEC only the combined and the L1I-at-width-8 effects
are measured.

**Results** (both finished 2026-11-09, no failures). Comparison pages:
`runs/sweep/20261109-1619-compare/` (both suites; agentic and SPEC
summaries merged per configuration with `runs/fe8-pl1i/merge_suites.py`)
and `20261109-1619-compare-agentic/` (adds the 2-cycle `pl1i`). Geomean
IPC change:

| configuration | agentic (vs base) | SPEC (vs width 6) |
|---|---|---|
| width 8 | +1.3% | +2.4% |
| perfect L1I, 2 cycles, width 6 | +9.6% | not run |
| width 8 + perfect L1I, 1 cycle | +14.5% | +8.2% |

Top-down, base → width 8 + perfect L1I at 1 cycle (mean share of slots):

| | agentic | SPEC |
|---|---|---|
| front-end bound | 42.5% → 17.8% | 42.2% → 19.1% |
| back-end bound | 34.5% → 51.5% | 29.0% → 45.3% |
| bad speculation | 8.2% → 13.7% | 6.2% → 11.1% |
| retiring | 14.9% → 17.0% | 22.6% → 24.6% |

Reading (provisional; top-down counters still experimental):
- The front end nearly stops being a limit, but most freed slots move to
  back-end bound (memory and core), not retiring: a front-end-bound slot
  is not a slot the back end could have used. Compare +48% from
  [[2026-11-02-perfect-l2]].
- Bad speculation grows about 1.7×: a faster front end fills more
  wrong-path slots before a mispredict resolves.
- SPEC has almost no L1I misses (0.015 per kilo-instruction), yet the
  1-cycle perfect L1I adds +5.7% over width 8 alone: that is the per-line
  hit wait ([[2026-11-05-front-end-width]]), a fetch-model cost present in
  every baseline.

## Width 8 and a 1-cycle real L1I, FDP on and off (2026-11-10)

**Question:** how much of that is the L1I hit latency alone, with a real
L1I (misses kept), and does FDP still matter at a 1-cycle hit?

**Switch:** `--l1i-cycles N` (`ef0ca350ae`) sets the real L1I's tag, data
and response latency (default 2). Validated on jq-2598 (2M + 3M,
`runs/l1i-latency/validate/`): no flag and `--l1i-cycles 2` identical;
at 1, fetch's I-cache stall cycles fall 6.6×.

**Sweeps** (`runs/l1i-latency/launch.sh`, settings as above):
`runs/sweep/20261110-0949-{fe8-l1i1,fe8-l1i1-nofdp,spec-fe8-l1i1,spec-fe8-l1i1-nofdp}`,
`--front-end-width 8 --l1i-cycles 1`, with and without `--disable-fdp`.
Baselines: `base`, `nofdp`, `fe8`, `spec-fe6`, `spec-fe8`, and the
1-cycle perfect-L1I sweeps above. No width-8 FDP-off baseline exists, so
FDP off is read against `nofdp` (width 6, 2 cycles).

**Results** (finished 2026-11-11 04:07, 106 runs, no failures; paused
about 2.5 h on 2026-11-10 to free memory for a build, no runs lost).
Pages: `runs/sweep/20261110-0949-compare-agentic/compare.html` (6
sweeps), `runs/sweep/20261110-0949-compare-spec/compare.html` (5) and
both suites on one page, `runs/sweep/20261110-0949-compare/compare.html`
(inputs merged into `runs/l1i-latency/merged/`).

IPC geomean change against width 6 with a 2-cycle L1I and FDP on
(`base` / `spec-fe6`):

| Configuration | Agentic | SPEC |
|---|---|---|
| width 8 | +1.3% | +2.4% |
| width 8, real L1I at 1 cycle | +4.6% | +6.4% |
| width 8, perfect L1I at 1 cycle | +14.5% | +8.2% |
| FDP off (width 6, 2 cycles) | −3.2% | — |
| width 8, real L1I at 1 cycle, FDP off | +3.0% | +5.3% |

Top-down (level 1, % of slots: front end / back end / bad speculation /
retiring):

| Configuration | Agentic | SPEC |
|---|---|---|
| width 6, 2 cycles | 42.5 / 34.5 / 8.2 / 14.9 | 42.2 / 29.0 / 6.2 / 22.6 |
| width 8 | 38.3 / 37.7 / 9.0 / 15.1 | 34.3 / 35.2 / 7.2 / 23.2 |
| width 8, real L1I at 1 cycle | 24.8 / 47.6 / 12.0 / 15.6 | 19.8 / 45.3 / 10.7 / 24.2 |
| width 8, perfect L1I at 1 cycle | 17.8 / 51.5 / 13.7 / 17.0 | 19.1 / 45.3 / 11.1 / 24.6 |
| width 8, real L1I at 1 cycle, FDP off | 28.0 / 45.2 / 11.4 / 15.4 | 22.2 / 44.0 / 9.9 / 23.9 |

Reading (provisional):
- **SPEC: the perfect-L1I gain is mostly the hit latency.** Of the +5.7%
  that the 1-cycle perfect L1I adds over width 8, the 1-cycle real L1I
  gives +3.9%, and its front-end bound (19.8%) is within a point of the
  perfect L1I's. This confirms the reading above: SPEC barely misses.
- **Agentic: misses still cost most of it.** The 1-cycle hit gives +3.3%
  over width 8; removing the misses as well gives a further +9.5%. The
  front-end bound falls 38.3% → 24.8% with the 1-cycle hit and to 17.8%
  with no misses. Fetch's I-cache stall cycles fall 5.4× with the 1-cycle
  hit and 25× with the perfect L1I (against `base`).
- **FDP is worth less at a 1-cycle hit.** FDP off costs 3.3% at width 6
  with 2 cycles, and 1.6% (agentic) or 1.0% (SPEC) at width 8 with 1
  cycle. Without FDP the L1I misses more (agentic 5.1 MPKI against 2.3
  with FDP) and the front-end bound is 3 points higher.
- **ITLB:** FDP off cuts the ITLB miss rate by about 10× (33 → 3 per
  kilo-instruction), as in the earlier sweep: most ITLB misses are FDP
  prefetch lookups.
- **More L1I misses with the faster hit.** With FDP on, agentic L1I MPKI
  rises 1.46 → 2.32 (×1.59) at the 1-cycle hit, and squashed instructions
  rise 1.7×. A guess, not checked: fetch runs further down wrong paths.
- As before, freed front-end slots go mostly to the back end and bad
  speculation, not to retiring.
