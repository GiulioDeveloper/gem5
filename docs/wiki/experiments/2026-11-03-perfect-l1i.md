# Limit study: perfect L1I

The `--perfect-l1i` model is built and validated. The sweep is planned (below). On
one 5M-instruction jq-2598 window, IPC goes from 0.760 to 0.845 (+11.2%).
That is a smoke-test number, not a result.

## Question

How much do L1I misses cost the agentic workloads? A perfect L1I always
hits at its normal hit latency, cold misses included. It is one piece of
the front-end upper bound; the others are the BTB
([[2026-10-16-btb-tlb-limit-study]]) and the ITLB (`--perfect-tlb`,
[[2026-11-02-perfect-l2]]).

## Model

`--perfect-l1i` (`--perfect-l1i-cycles N`, default 2) sets the O3 params
`perfectICache` and `perfectICacheLatency`. In `Fetch::finishTranslation`,
`sendPerfectICacheRead` replaces `icachePort.sendTimingReq`:

- **Functional read, timed delivery.** The fetch block is read with
  `sendFunctional` on the I-cache port. An auto-deleting event delivers it
  to `processCacheCompletion` N cycles later. Fetch goes through the same
  `IcacheWaitResponse` state as with a timed hit. Each read is counted in
  `fetch.perfectICacheReads`.
- **N = the L1I hit latency.** A timed hit responds at
  `clockEdge(max(tag_latency, data_latency))` (`BaseCache::
  calculateAccessLatency`, `sequential_access` off), which is 2 cycles for
  `L1I`. The default reads it from the `L1I` class.
- **Correct code under JIT.** A functional read snoops every cache, so code
  that is still dirty in the L1D is fetched correctly.
- **Squashes and drain.** A read squashed in flight is dropped by the
  existing `pkt->req != memReq` check (`fetch.icacheSquashes`).
  `Fetch::isDrained` waits until no perfect read is in flight, so the CPU
  cannot switch out while one is pending.
- **The ITLB is untouched.** Translation still runs timed.

**The hierarchy sees no instruction traffic.** This was the user's choice,
for simplicity. The L1I gets no accesses. The L2 holds no instruction
lines and spends no bandwidth or MSHRs on them, so **data gets all of the
L2's capacity and bandwidth**. The speedup therefore mixes the front-end
gain with a data-side gain. The FDP prefetcher is detached because it
issues from FTQ inserts and would keep pushing instruction lines into the
L2. The decoupled front end stays on, unlike with `--disable-fdp`. The
tagged L1I prefetcher stays attached but never fires. Banner:
`L1I perfect (2 cyc)`, `FDP=off`.

**Option not built: a shadow request.** Fetch would still send the timed
request, keeping the L1I/L2 state and traffic as in the baseline, but would
not wait for it. That would separate the front-end gain from the L2
relief. Set aside for simplicity.

## Validation (2026-11-03)

Run: jq-2598, 2M warm-up and 5M detailed instructions in 1M blocks.
Baseline, perfect and a perfect repeat, `runs/perfect-l1i/validate.sh`; the
readout is `runs/perfect-l1i/compare.py`. One window only.

| | baseline | perfect L1I | perfect repeat |
|---|---|---|---|
| IPC | 0.7597 | 0.8448 | 0.8448 |
| fetch lines (`fetch.cacheLines`) | 1,187,942 | 1,201,748 | 1,201,748 |
| `perfectICacheReads` | 0 | 1,201,748 | 1,201,748 |
| L1I demand accesses / misses | 1,187,935 / 12,494 | 0 / 0 | 0 / 0 |
| fetch cycles in `icacheWaitResponse` | 1,412,435 | 1,239,752 | 1,239,752 |
| L2 demand accesses | 154,215 | 68,416 | 68,416 |
| L1D avg MSHR miss latency (cycles) | 83.8 | 75.1 | 75.1 |

- **Switch off is a no-op:** the baseline matches the perfect-L2 baseline
  (`runs/perfect-l2/validate/baseline`) on IPC and L1D misses.
- **Determinism:** the two perfect runs match on every number.
- **No instruction traffic:** every fetch line is a perfect read; the L1I
  sees no access and issues no prefetch.
- **The L2 sees 56% fewer accesses,** and the L1D miss latency falls from
  83.8 to 75.1 cycles. That is the data-side gain mixed into the +11.2%.
  How much of the gain it accounts for is not measured.
- **Fetch still waits about one cycle per line.** `icacheWaitResponse`
  drops by only 12% (1.41M to 1.24M cycles), about 1.03 cycles per fetch
  line with the perfect L1I. Most of the baseline's wait is the 2-cycle
  hit, not misses. The cause is in the code: fetch holds one 64-byte fetch
  buffer and has at most one I-cache request in flight per thread. The
  early ("pipelined") request is issued only when fetch crosses into the
  next line, and not while a request is pending (`issuePipelinedIfetch`,
  `fetch.cc`). So each new line, sequential or after a taken branch, waits
  for the hit latency even when the hit is guaranteed. Waiting cycles are
  not necessarily lost cycles: the 32-µop fetch queue can hide them from
  decode. Their IPC cost is not measured.

## Planned sweep

Nine agentic-only smart sweeps, `runs/sweep/<stamp>-<name>`: 27 tasks each, 1B detailed
instructions after 20M of warm-up, 200K blocks, `COMPRESS_STATS=1`, first
launched at commit `f15bdb37f0`. Launcher and comparisons: `runs/perfect-sweep/launch.sh`,
`compare.sh`.

| sweep | flags | compared against |
|---|---|---|
| `base` | none | |
| `nofdp` | `--disable-fdp` | `base` |
| `ptlb` | `--perfect-tlb` | `base` |
| `pl1i` | `--perfect-l1i` | `base` |
| `pl1i-ptlb` | `--perfect-l1i --perfect-tlb` | `base` |
| `pl2` | `--perfect-l2` | `base` |
| `pl2-ptlb` | `--perfect-l2 --perfect-tlb` | `base` |
| `pl2-nofdp` | `--perfect-l2 --disable-fdp` | `nofdp` |
| `pl2-nofdp-ptlb` | `--perfect-l2 --disable-fdp --perfect-tlb` | `nofdp` |

- **Launch order:** `base`, `pl2` and `pl1i` first; the other six start
  once those three have launched all their runs.
- **"FDP off" here is `--disable-fdp`**, which turns off the whole decoupled
  front end, as in [[2026-10-14-fdp-off-sweep]]. `--perfect-l1i` only
  detaches the FDP prefetcher.

A first launch (2026-11-03) was stopped after about 40 minutes, with no
run finished, and its directories deleted. The sweep waits for top-down
counters, to be added to gem5 in a separate piece of work, so the results
can be analysed with them.
